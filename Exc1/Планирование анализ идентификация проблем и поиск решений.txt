Существующие и потенциальные проблемные места
- каждое приложение имеет по одному экземпляру
- каждое приложение разворачивается на виртуалке
- один инстанс БД для записи и чтения
- MES API и сам сервис расчета стоимости. Сервис расчета и так не быстрый и грузит приложение скорее всего,
  еще добавились и внешние вызовы через API
- MES для операторов вызывает MES API, который может быть загружен расчетом стоимости заказа

Инициативы для устранения нежелательных ситуаций в порядке приоритета
1) увеличить количество инстансов MES API (чтобы снизить нагрузку на сервис)
2) добавить реплики для БД и реализовать чтение сначала из реплик (так как это наиболее часто выполняемые операции)
3) в сервис MES добавить circuit breaker, для того чтобы не ддосить сервис MES API, который и так загружен

4) между сервисами MES API и MES реализовать BackPressure (MES API сообщает о своей загруженности)
5) разбить сервис MES API на два микро сервиса (первый выполняет расчет стоимости производства изделия, второй принимает запросы от пользователя MES API)
6) увеличить количество инстансов каждого из приложений (чтобы снизить нагрузку на сервисы)
7) добавить кэширование запросов для пользователей (информация меняется не очень часто для них)
8) добавить мониторинг
9) проанализировать, какие логи есть, достаточно ли их, если нет, то добавить нужные логи
10) в будущем добавить трейсинг, чтобы точно отслеживать, где зависает запрос
11) внедрить контейнеризацию и перевести развертывания приложений в k8s
12) для поддержки контейнеризации нужны будут еще DevOps-инженеры (1,2)

Такой порядок обоснован тем, что в первую очередь необходимо как можно быстрее снизить количество возникших проблем.
А на первый взгляд кажется очевидным, что мощностей не хватает, поэтому логично изменить мощности серверов в EC2.

Целевая архитектура через пол года:
1) в сервис MES добавлен circuit breaker, для того чтобы не ддосить сервис MES API, который и так загружен
2) сервис MES API разбит на два микро сервиса (первый выполняет расчет стоимости производства изделия, второй принимает запросы от пользователя MES API)
3) добавлен мониторинг, логирование и трейсинг (чтобы ьыстрее находить проблемные места)
4) добавлено кэширование запросов для пользователей (чтобы увеличить скорость обработки запросов)
5) расширена команда DevOps-инженеров (для реализации контейнеризации)
6) внедрена контейнеризация (для быстрой масштабируемости системы)

Если есть возможность выполнить только три пункта из списка инициатив в ближайшие полгода, то это:
1) увеличить количество инстансов MES API (чтобы снизить нагрузку на сервис)
2) добавить кэширование запросов, чтобы снизить нагрузку на БД
3) в сервис MES добавить circuit breaker, для того чтобы не ддосить сервис MES API, который и так загружен
